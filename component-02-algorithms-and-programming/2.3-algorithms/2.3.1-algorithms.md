## Key terms

| Term | Definition |
|------|-----------|
| **Algorithm** | A precise, step-by-step procedure for solving a problem |
| **Trace** | Working through an algorithm manually, recording the state at each step |
| **Linear search** | Checking each element one at a time from start to end until the target is found |
| **Binary search** | Repeatedly halving a sorted list to find the target; much faster than linear search |
| **Bubble sort** | Repeatedly swapping adjacent elements if they are in the wrong order |
| **Merge sort** | Recursively splitting a list in half, sorting each half, then merging them |
| **Insertion sort** | Building a sorted list one element at a time by inserting each into its correct position |
| **Quick sort** | Choosing a pivot, partitioning around it, then recursively sorting each partition |
| **Dijkstra's algorithm** | Finds the shortest path from a source vertex to all other vertices in a weighted graph |
| **A* (A-star)** | A graph search algorithm using a heuristic to prioritise paths likely to reach the goal |
| **Heuristic** | An estimate or rule of thumb that guides a search (e.g. straight-line distance to goal) |
| **Big O notation** | A mathematical notation describing how an algorithm's time or space requirements grow with input size |
| **Time complexity** | How the running time of an algorithm scales with the size of the input (n) |
| **Divide and conquer** | Breaking a problem into smaller sub-problems, solving each, then combining results |

## Core notes

### Big O notation

Big O describes the **worst-case** growth rate of an algorithm — how much slower it gets as the input size (n) grows.

| Complexity | Name | Example |
|-----------|------|---------|
| **O(1)** | Constant | Accessing an array element by index |
| **O(log n)** | Logarithmic | Binary search |
| **O(n)** | Linear | Linear search; single loop over n items |
| **O(n log n)** | Linearithmic | Merge sort, quick sort (average) |
| **O(n²)** | Quadratic | Bubble sort, insertion sort (worst case) |

> The lower the Big O class, the better the algorithm scales for large inputs.

### Linear search

Check each element in turn. Works on **unsorted** lists.

```
FUNCTION linearSearch(arr, target)
    FOR i ← 0 TO LEN(arr) - 1
        IF arr[i] = target THEN
            RETURN i
        ENDIF
    ENDFOR
    RETURN -1   // not found
ENDFUNCTION
```

- **Best case:** O(1) — target is the first element
- **Worst case:** O(n) — target is last or not present

### Binary search

Requires a **sorted** list. Repeatedly halves the search space.

```
FUNCTION binarySearch(arr, target)
    low ← 0
    high ← LEN(arr) - 1
    WHILE low ≤ high DO
        mid ← (low + high) DIV 2
        IF arr[mid] = target THEN
            RETURN mid
        ELSE IF arr[mid] < target THEN
            low ← mid + 1
        ELSE
            high ← mid - 1
        ENDIF
    ENDWHILE
    RETURN -1
ENDFUNCTION
```

- **Worst case:** O(log n)

### Bubble sort

Repeatedly passes through the list, swapping adjacent elements if out of order. After each pass, the largest unsorted element "bubbles" to the end.

```
PROCEDURE bubbleSort(arr)
    n ← LEN(arr)
    FOR i ← 0 TO n - 2
        FOR j ← 0 TO n - 2 - i
            IF arr[j] > arr[j + 1] THEN
                temp ← arr[j]
                arr[j] ← arr[j + 1]
                arr[j + 1] ← temp
            ENDIF
        ENDFOR
    ENDFOR
ENDPROCEDURE
```

- **Best case:** O(n) — with early-exit optimisation when no swaps occur
- **Worst case:** O(n²)

### Merge sort

**Divide and conquer.** Split the list in half recursively until single elements, then merge sorted halves.

```
FUNCTION mergeSort(arr)
    IF LEN(arr) ≤ 1 THEN RETURN arr ENDIF
    mid ← LEN(arr) DIV 2
    left ← mergeSort(arr[0 .. mid - 1])
    right ← mergeSort(arr[mid .. LEN(arr) - 1])
    RETURN merge(left, right)
ENDFUNCTION
```

- **All cases:** O(n log n)
- Uses additional memory for the merge step — not **in-place**

### Insertion sort

Builds a sorted sub-list by taking each element and inserting it into its correct position.

```
PROCEDURE insertionSort(arr)
    FOR i ← 1 TO LEN(arr) - 1
        key ← arr[i]
        j ← i - 1
        WHILE j ≥ 0 AND arr[j] > key DO
            arr[j + 1] ← arr[j]
            j ← j - 1
        ENDWHILE
        arr[j + 1] ← key
    ENDFOR
ENDPROCEDURE
```

- **Best case:** O(n) — already sorted
- **Worst case:** O(n²) — reverse sorted

### Quick sort

Selects a **pivot**, partitions elements around it (smaller to left, larger to right), then recursively sorts each partition.

- **Average case:** O(n log n)
- **Worst case:** O(n²) — when the pivot is always the smallest or largest element (e.g. already sorted list with first-element pivot)
- **In-place** — does not need extra memory like merge sort

### Dijkstra's shortest path algorithm

Finds the **shortest path** from a source vertex to all others in a **weighted graph** (non-negative weights only).

**Steps:**
1. Assign distance 0 to source, ∞ to all others
2. Mark all vertices as unvisited
3. For the current vertex, update the distance of each unvisited neighbour:  
   `new_dist = current_dist + edge_weight`  
   If new_dist < stored distance, update it
4. Mark current vertex as visited; move to the unvisited vertex with the smallest known distance
5. Repeat until all vertices are visited

- **Time complexity:** O(n²) with simple implementation; O((n + e) log n) with a priority queue (where e = number of edges)

### A* search algorithm

An **informed** search that uses Dijkstra's approach plus a **heuristic** (h(n)) — an estimate of the remaining distance to the goal.

- **f(n) = g(n) + h(n)** where g(n) = actual cost from start; h(n) = estimated cost to goal
- Always explores the path with the lowest f(n) next
- Finds the **optimal** path if the heuristic is **admissible** (never overestimates)
- Faster than Dijkstra's in many real-world scenarios

| Feature | Dijkstra's | A* |
|---------|-----------|-----|
| **Uses heuristic** | No | Yes |
| **Finds shortest path** | Always | Yes (if heuristic admissible) |
| **Explores unnecessarily** | More | Less (guided by heuristic) |
| **Use case** | Shortest path to all vertices | Shortest path to a specific goal |

## Worked examples

### Example 1 — Binary search trace

Array (sorted): `[4, 9, 15, 23, 31, 42, 58]`  
Target: `31`

| Step | low | high | mid | arr[mid] | Action |
|------|-----|------|-----|----------|--------|
| 1 | 0 | 6 | 3 | 23 | 23 < 31 → low = 4 |
| 2 | 4 | 6 | 5 | 42 | 42 > 31 → high = 4 |
| 3 | 4 | 4 | 4 | 31 | Found at index 4 ✓ |

### Example 2 — Bubble sort trace

Array: `[5, 3, 8, 1]`

**Pass 1:** Compare 5,3 → swap → [3,5,8,1]; compare 5,8 → ok; compare 8,1 → swap → [3,5,1,8]  
**Pass 2:** Compare 3,5 → ok; compare 5,1 → swap → [3,1,5,8]  
**Pass 3:** Compare 3,1 → swap → [1,3,5,8]  
**Result:** [1, 3, 5, 8] ✓

### Example 3 — Dijkstra's algorithm trace

Graph:
```
     A
    /|\
   4 | 2
  /  |  \
 B   |   C
  \  |  /
   3 | 1
    \|/
     D
```
Edges: A-B(4), A-C(2), A-D(7) [not shown], B-D(3), C-D(1)

| Step | Visited | Dist A | Dist B | Dist C | Dist D |
|------|---------|--------|--------|--------|--------|
| Start | — | 0 | ∞ | ∞ | ∞ |
| Visit A | {A} | 0 | 4 | 2 | 7 |
| Visit C (min) | {A,C} | 0 | 4 | 2 | 3 (via C: 2+1) |
| Visit D (min) | {A,C,D} | 0 | 4 | 2 | 3 |
| Visit B (min) | {A,C,D,B} | 0 | 4 | 2 | 3 |

Shortest paths from A: A→B=4, A→C=2, A→D=3 (via C)

## Common mistakes

- ❌ **Mistake:** Using binary search on an unsorted array.  
  ✅ **Correction:** Binary search **requires** the data to be sorted first.

- ❌ **Mistake:** Saying bubble sort is always O(n²).  
  ✅ **Correction:** With an early-exit optimisation (stop if no swaps in a pass), best case is O(n) for an already-sorted list.

- ❌ **Mistake:** Saying merge sort is in-place.  
  ✅ **Correction:** Merge sort requires additional memory for the merge step — it is **not** in-place. Quick sort is in-place.

- ❌ **Mistake:** Applying Dijkstra's to a graph with negative edge weights.  
  ✅ **Correction:** Dijkstra's does not work correctly with negative weights. Use Bellman-Ford for graphs with negative edges.

- ❌ **Mistake:** Saying A* is always faster than Dijkstra's.  
  ✅ **Correction:** A* is faster when a good heuristic is available. A poor heuristic can make A* slower.

## Exam focus

- **Trace** — step-by-step traces of binary search, bubble sort, and Dijkstra's (very common — show **all** intermediate states)
- **Write** — pseudocode for linear/binary search, bubble sort, or simple recursive algorithms
- **Compare** — merge sort vs quick sort; Dijkstra's vs A*; binary search vs linear search
- **Explain** — what Big O notation means; why O(n log n) is better than O(n²) for large n
- **Evaluate** — which algorithm/structure is most suitable for a given scenario

> 💡 Algorithm **trace questions** are almost guaranteed in Component 02 exams. Practise showing the full state of the data structure after **every single step** — partial traces often lose marks.

## Quick-check questions

1. What is the Big O complexity of binary search in the worst case?
2. Why must the data be sorted before binary search can be applied?
3. After the first full pass of bubble sort on [5, 3, 8, 1], what is the array state?
4. What is the key difference between merge sort and quick sort in terms of memory use?
5. What does Dijkstra's algorithm find?
6. What is a heuristic and how does A* use it?
7. Order these from best to worst Big O: O(n²), O(log n), O(n), O(1), O(n log n).

<details>
<summary>Outline answers</summary>

1. O(log n).
2. Binary search relies on the sorted order to determine which half to eliminate; it doesn't work on unsorted data.
3. [3, 5, 1, 8] — the 8 "bubbles" to the end.
4. Merge sort is not in-place (requires extra memory for merged arrays); quick sort is in-place.
5. The shortest path from a source vertex to all other vertices in a weighted graph.
6. A heuristic is an estimate of the remaining cost to the goal. A* uses it to prioritise paths with a lower estimated total cost (f = g + h), exploring more promising routes first.
7. O(1) < O(log n) < O(n) < O(n log n) < O(n²) — from best to worst.

</details>
