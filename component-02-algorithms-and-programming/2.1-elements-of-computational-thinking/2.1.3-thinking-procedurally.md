# 2.1.3 Thinking Procedurally

> **Component:** 02 — Algorithms and Programming | **Section:** 2.1 | **Sub-section:** 2.1.3

---

## What you need to know

Procedural thinking involves **breaking down problems** into smaller, manageable parts — and then defining the order in which those parts should be executed. This is the foundation of structured programming and software design.

## Key terms

| Term | Definition |
|------|-----------|
| **Decomposition** | Breaking a complex problem into smaller, more manageable sub-problems |
| **Top-down design** | Starting with the high-level problem and breaking it down into sub-problems recursively |
| **Hierarchy chart** | A diagram showing the decomposition of a program into procedures and sub-procedures |
| **Stepwise refinement** | Progressively adding detail to a design — starting from a high-level description and refining it step by step |
| **Sequence** | Instructions executed one after another in order |
| **Selection** | Choosing which path to follow based on a condition (IF/ELSE) |
| **Iteration** | Repeating a block of instructions (loops) |
| **Subroutine** | A named block of code that can be called from multiple places |

## Core notes

### Decomposition

A large, complex problem is broken into sub-problems, which can be broken down further, until each piece is small enough to implement.

**Example — decomposing a "library system":**
```
Library System
├── Manage Books
│   ├── Add book
│   ├── Remove book
│   └── Search books
├── Manage Members
│   ├── Register member
│   └── Remove member
└── Manage Loans
    ├── Issue book
    ├── Return book
    └── View overdue loans
```

**Benefits of decomposition:**
- Easier to understand and work with
- Different parts can be developed and tested independently
- Sub-problems can be assigned to different team members
- Encourages code reuse

### Hierarchy charts

A diagram showing decomposition visually. Boxes represent sub-problems; connections show relationships.

### Sequence, selection, iteration

Every structured program is built from these three constructs:

| Construct | Description | Example |
|-----------|------------|---------|
| **Sequence** | Steps run in order, one after another | Assignment, then print |
| **Selection** | A condition determines which branch runs | IF score > 50 THEN... |
| **Iteration** | A block repeats while (or until) a condition holds | FOR loop, WHILE loop |

### Stepwise refinement

Starting from a high-level description:
1. "Sort a list" → "Compare adjacent elements and swap if out of order, repeat"
2. → Write the outer loop, inner loop, swap logic as pseudocode
3. → Translate to actual code

Each step adds more detail until the design is specific enough to implement.

## Common mistakes

- ❌ **Mistake:** Thinking decomposition just means listing what a program does.  
  ✅ **Correction:** Decomposition breaks the problem into independent, manageable sub-problems — each should have a clear, single purpose.
