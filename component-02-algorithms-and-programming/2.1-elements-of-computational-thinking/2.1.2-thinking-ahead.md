# 2.1.2 Thinking Ahead

> **Component:** 02 — Algorithms and Programming | **Section:** 2.1 | **Sub-section:** 2.1.2

---

## What you need to know

Thinking ahead means planning before you act — anticipating inputs, outputs, pre-conditions, and potential problems before writing any code or algorithm. This underpins good software design and is a key computational thinking skill.

---

## Specification points

- [ ] (a) Identifying inputs and outputs for a given problem
- [ ] (b) Pre-conditions — what must be true before a process can run
- [ ] (c) Caching — storing results of computations so they can be reused
- [ ] (d) Prefetching — loading data before it is needed to reduce waiting time
- [ ] (e) Reusable program components — designing subroutines/libraries for reuse

## Key terms

| Term | Definition |
|------|-----------|
| **Pre-condition** | A condition that must be true before a subroutine or process can execute correctly |
| **Post-condition** | A condition that is guaranteed to be true after a subroutine executes correctly |
| **Caching** | Storing the results of expensive computations or frequent data accesses for quick reuse |
| **Prefetching** | Loading data or instructions into cache before they are actually requested |
| **Reusable component** | A subroutine, module, or library designed to be used in multiple contexts |

---

## Core notes

### Thinking about inputs and outputs

Before writing an algorithm, clearly define:
- **What inputs** does this process receive? (type, range, format)
- **What outputs** should it produce? (type, format, what they mean)

Example — before writing a sorting subroutine:
- Input: an unsorted array of integers; the array length
- Output: the same array sorted in ascending order; or a new sorted array

### Pre-conditions

A pre-condition is a **guarantee about the input** that must hold before the procedure runs.

- Binary search **pre-condition:** the input array must be sorted
- Square root function **pre-condition:** the input must be non-negative

If a pre-condition is not met, the result is undefined — the procedure may give wrong answers or crash.

Pre-conditions are part of thinking ahead: a good programmer identifies what must be true before running code and either validates inputs or documents pre-conditions clearly.

### Caching

Caching stores the result of a computation so it can be quickly retrieved next time, rather than recomputed.

**Examples:**
- A web browser caches images — the same image on multiple pages is only downloaded once
- A function result is cached if it is called repeatedly with the same input (memoisation)
- CPU cache stores frequently accessed memory locations (see 1.1.1)

**Trade-off:** Cache uses memory; it is only worth caching if the cost of recomputation exceeds the cost of storage.

### Prefetching

Prefetching loads data into a faster storage tier **before** it is explicitly requested.

- CPU prefetches the next instructions while executing the current one (pipeline)
- A video streaming service buffers (prefetches) the next few seconds of video

**Benefit:** Reduces waiting time — data is ready when needed.  
**Risk:** If the prefetched data is not used (e.g. user changes video), bandwidth is wasted.

### Reusable components

Good programs are built from **modular, reusable subroutines**. When designing a subroutine for reuse:
- It should have a clearly defined purpose
- Parameters should be used rather than global variables
- It should work correctly for all valid inputs (as defined by pre-conditions)
- It should be tested independently

**Libraries** are collections of reusable components (e.g. Python's `math` library).

## Worked examples

### Example — Pre-conditions for a binary search

```
FUNCTION binarySearch(arr, target)
// Pre-condition: arr must be sorted in ascending order
// Pre-condition: arr must not be empty
```

A caller who passes an unsorted array violates the pre-condition — the result is unreliable.

### Example — Caching (memoisation)

Without caching, calculating Fibonacci(40) requires millions of recursive calls.  
With caching:
```
memo = {}
FUNCTION fib(n)
    IF n IN memo THEN RETURN memo[n] ENDIF
    IF n <= 1 THEN RETURN n ENDIF
    result ← fib(n-1) + fib(n-2)
    memo[n] ← result
    RETURN result
ENDFUNCTION
```
Each value is computed only once → O(n) instead of O(2^n).

## Common mistakes

- ❌ **Mistake:** Thinking pre-conditions are optional comments.  
  ✅ **Correction:** Pre-conditions are **requirements** — if they are not met, the subroutine may produce incorrect results. They should be validated or clearly documented.

- ❌ **Mistake:** Confusing caching and prefetching.  
  ✅ **Correction:** Caching **stores computed results** for reuse. Prefetching **loads data in advance** before it is requested.

## Quick-check questions

1. What is a pre-condition?
2. Give an example of a pre-condition for a binary search algorithm.
3. What is the purpose of caching?
4. What is prefetching and where is it used?
5. Why is designing reusable subroutines important?

<details>
<summary>Outline answers</summary>

1. A condition that must be true before a subroutine or process executes correctly.
2. The input array must be sorted in ascending order.
3. To store the results of expensive/frequent computations so they can be quickly retrieved without recomputation.
4. Loading data or instructions into faster memory before they are actually needed, to reduce latency. Used in CPU pipelines and video buffering.
5. Reduces duplication; saves development time; reusable components can be tested once and trusted; improves maintainability.

</details>
