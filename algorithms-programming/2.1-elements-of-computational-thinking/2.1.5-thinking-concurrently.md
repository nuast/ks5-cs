# 2.1.5 Thinking Concurrently

> **Component:** 02 — Algorithms and Programming | **Section:** 2.1 | **Sub-section:** 2.1.5

---

## What you need to know

Thinking concurrently is about recognising when parts of a problem can be solved **at the same time** — in parallel — rather than one after another. This is increasingly important as computers have multiple cores and tasks are distributed across networks.

## Key terms

| Term | Definition |
|------|-----------|
| **Concurrent processing** | Multiple tasks making progress at the same time (not necessarily simultaneously on the same processor) |
| **Parallel processing** | Multiple tasks executing simultaneously on multiple processors/cores |
| **Thread** | A unit of execution within a process; multiple threads can run concurrently within one process |
| **Race condition** | When two concurrent processes access shared data and the outcome depends on the order they execute |
| **Deadlock** | When two or more processes are each waiting for the other to release a resource, so none can proceed |
| **Mutex / lock** | A mechanism for ensuring only one thread accesses a shared resource at a time |

---

## Core notes

### When can tasks be concurrent?

Tasks can be run concurrently when they are **independent** — they do not rely on each other's results.

**Example — making breakfast:**
- Sequential: boil kettle → make toast → pour juice → eat
- Concurrent: start kettle AND start toaster simultaneously; pour juice while they run

**Computing example:**
- A web server handling multiple requests simultaneously
- A program rendering different parts of a 3D scene on different cores
- A merge sort splitting into independent sub-sorts (divide and conquer)

### Benefits of concurrent processing

- **Faster completion** for tasks that can be parallelised
- **Better hardware utilisation** — uses multiple cores
- **Improved responsiveness** — UI stays responsive while background tasks run

### Issues with concurrent processing

**Race condition:**
- Two threads read and write a shared variable simultaneously
- The result depends on which thread runs first — unpredictable behaviour

```
Thread A: balance = balance + 100
Thread B: balance = balance - 50
// If both read balance=1000 simultaneously, one update may be lost
```

**Deadlock:**
- Thread A holds Resource 1 and waits for Resource 2
- Thread B holds Resource 2 and waits for Resource 1
- Neither can proceed — system is stuck

**Solutions:**
- **Mutex/lock** — only one thread can hold the lock at a time
- **Careful resource ordering** — always acquire resources in the same order
- **Timeout** — if a resource cannot be acquired within a time limit, release held resources and retry

---

## Common mistakes

- ❌ **Mistake:** Saying all tasks can be run concurrently.  
  ✅ **Correction:** Tasks that depend on each other's output (data dependencies) must be sequential. Only independent tasks can be concurrent.

- ❌ **Mistake:** Confusing concurrent and parallel processing.  
  ✅ **Correction:** **Concurrent** = tasks make progress at overlapping times (may not be simultaneously). **Parallel** = tasks execute at exactly the same moment on multiple processors.

## Quick-check questions

1. What is concurrent processing?
2. Give two tasks that could be done concurrently in a computer program.
3. What is a race condition?
4. What is deadlock?

<details>
<summary>Outline answers</summary>

1. Multiple tasks making progress at overlapping times — may be on one processor (time-sliced) or multiple processors.
2. Any two independent tasks: rendering UI while processing in background / handling multiple network requests / parallel sub-sorts.
3. When two concurrent processes access shared data and the outcome depends on execution order — leads to unpredictable results.
4. When two processes each hold a resource the other needs, and neither can proceed.

</details>
