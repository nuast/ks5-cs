# 1.3.1 Compression, Encryption and Hashing

> **Component:** 01 — Computer Systems | **Section:** 1.3 | **Sub-section:** 1.3.1

---

## What you need to know

This topic covers three fundamental techniques for handling data: **compression** (making files smaller), **encryption** (making data unreadable to unauthorised parties), and **hashing** (creating a fixed-length fingerprint of data). These techniques underpin almost all modern data exchange and security.

## Key terms

| Term | Definition |
|------|-----------|
| **Compression** | Reducing the size of a file for storage or transmission |
| **Lossy compression** | Some data is permanently discarded to achieve greater compression; quality degrades |
| **Lossless compression** | No data is lost; original file can be perfectly reconstructed |
| **Run-length encoding (RLE)** | Replacing repeated data with a count and value (e.g. AAABBB → 3A3B) |
| **Encryption** | Transforming data so that it cannot be read without the correct key |
| **Plaintext** | Original, unencrypted data |
| **Ciphertext** | Encrypted data |
| **Symmetric encryption** | Same key used to encrypt and decrypt (e.g. AES) |
| **Asymmetric encryption** | A key pair: public key encrypts; private key decrypts (e.g. RSA) |
| **Public key** | Shared openly; used to encrypt data or verify a signature |
| **Private key** | Kept secret; used to decrypt data or create a signature |
| **Hash function** | A one-way function that produces a fixed-length output (hash/digest) from any input |
| **Collision** | Two different inputs producing the same hash output |
| **Digital signature** | A hash of a message, encrypted with the sender's private key, used to verify authenticity |
| **Digital certificate** | A document that binds a public key to an identity, signed by a trusted Certificate Authority |

## Core notes

### Compression

**Lossy:** Data is removed permanently. Used where some quality loss is acceptable.  
- JPEG images, MP3 audio, MP4 video
- Cannot reconstruct original exactly

**Lossless:** All original data preserved.  
- PNG images, ZIP archives, GIF
- Must be used for text, code, or where exact reproduction is required

### Run-length encoding (RLE)

Replace runs of repeated data with (count, value) pairs.

Example (bitmap row):
```
WWWWWBBBWWW → (4,W)(3,B)(3,W)
```

- Effective for images with large uniform areas (e.g. simple logos, cartoons)
- Ineffective for complex images with little repetition (e.g. photographs)

### Symmetric vs asymmetric encryption

**Symmetric:**
- Same key encrypts and decrypts
- Fast and efficient for large amounts of data
- **Problem:** how to securely share the key with the recipient?
- Examples: AES, DES

**Asymmetric:**
- Two keys: public (shared freely) and private (kept secret)
- Data encrypted with public key → only decryptable with the corresponding private key
- Solves the key distribution problem
- Slower than symmetric encryption
- Used in HTTPS to securely exchange a symmetric session key

**HTTPS key exchange (simplified):**
1. Server sends its public key (in a digital certificate)
2. Client verifies the certificate (is it signed by a trusted CA?)
3. Client generates a symmetric session key, encrypts it with server's public key
4. Server decrypts with its private key → both now share the session key
5. Further communication uses fast symmetric encryption

### Hashing

- A hash function takes input of any length and produces a **fixed-length** output
- One-way — it is computationally infeasible to reverse (find input from output)
- The same input always produces the same output
- A small change in input causes a completely different hash (avalanche effect)

**Uses:**
- **Password storage** — store hash of password, not plaintext
- **Data integrity** — checksums to verify a file has not been corrupted
- **Digital signatures**
- **Hash tables** (see 1.4.2)

**Password checking:**
```
User types password → hash it → compare to stored hash
(Never compare or store the plaintext password)
```

### Digital signatures

Allow the recipient to verify the **authenticity** (who sent it) and **integrity** (not tampered with) of a message.

1. Sender creates a **hash** of the message
2. Sender encrypts the hash using their **private key** → this is the digital signature
3. Recipient decrypts the signature using sender's **public key** → recovers the original hash
4. Recipient independently hashes the received message
5. If the two hashes match → message is authentic and unmodified

## Worked examples

### Example 1 — RLE compression

Image row (24 pixels): `RRRRRRRRGGGGGGBBBBBB`
- Without RLE: 24 characters
- With RLE: `8R6G6B` → 6 characters (75% reduction)

### Example 2 — Hashing for password storage

User sets password `"MySecret123"`:
- System hashes: `SHA-256("MySecret123")` → `a3f8...7d2` (64 hex chars)
- Only the hash is stored in the database

User logs in:
- User enters `"MySecret123"` → system hashes it → compare to stored hash
- If match → authenticated

If the database is stolen, attackers see only hashes, not passwords.

## Common mistakes

- ❌ **Mistake:** Saying asymmetric encryption uses the private key to encrypt.  
  ✅ **Correction:** In standard encryption, the **public key** encrypts and the **private key** decrypts. (Note: in digital signatures the roles are reversed for signing, but this is signing, not encryption.)

- ❌ **Mistake:** Saying lossless compression always produces smaller files than lossy.  
  ✅ **Correction:** Lossy compression typically achieves much greater compression ratios. Lossless compression preserves all data but may not reduce size as much.

- ❌ **Mistake:** Saying a hash function can be reversed.  
  ✅ **Correction:** Hash functions are **one-way** — it is computationally infeasible to determine the original input from the hash.

## Quick-check questions

1. Give one difference between lossy and lossless compression.
2. Apply RLE to: `AAABBCCCCCD`
3. What is the main disadvantage of symmetric encryption compared to asymmetric?
4. Why is a password stored as a hash rather than in plaintext?
5. What is a digital signature and what does it verify?

<details>
<summary>Outline answers</summary>

1. Lossy: data permanently removed / quality reduced. Lossless: all data preserved / original can be reconstructed.
2. `3A2B5C1D` (3A, 2B, 5C, 1D).
3. Key distribution — how to securely share the key with the recipient.
4. If the database is compromised, attackers see only hashes not passwords; the original password cannot be derived from the hash.
5. A digital signature is an encrypted hash of a message (encrypted with sender's private key). It verifies authenticity (who sent it) and integrity (not tampered with).

</details>
