# 1.2.3 Software Development

## What you need to know

This topic covers how software is planned, built, and tested. You need to know the main **software development methodologies** (systematic approaches to building software), understand their strengths and weaknesses, and be able to **compare** them. OCR also expects you to know the key stages of each model and be able to **evaluate which methodology suits a given scenario**.

## Key terms

| Term | Definition |
|------|-----------|
| **Methodology** | A structured approach to planning, developing, and managing a software project |
| **Waterfall model** | A sequential, linear development model with distinct stages; each stage must complete before the next begins |
| **Agile** | An iterative, flexible development approach where software is built in small increments with frequent stakeholder feedback |
| **Iteration** | One complete cycle of design → build → test within an agile/spiral method |
| **Sprint** | A fixed time period (typically 1–4 weeks) in which an agile team completes a set of features |
| **Prototype** | An early, incomplete version of the software used to gather feedback |
| **Extreme Programming (XP)** | An agile method emphasising pair programming, continuous testing, and frequent small releases |
| **Pair programming** | Two developers work at one machine — one writes code, the other reviews it in real time |
| **Test-driven development (TDD)** | Writing automated tests *before* writing the code that makes them pass |
| **Spiral model** | An iterative model where each loop includes planning, risk analysis, development, and evaluation |
| **RAD** | Rapid Application Development — prioritises prototyping and user feedback over rigid planning |
| **Alpha testing** | Internal testing by developers/staff before release |
| **Beta testing** | Testing by a limited group of real end-users before full release |
| **Acceptance testing** | The client verifies that the system meets their agreed requirements |

## Core notes

### Waterfall model

A **linear, sequential** approach. Stages flow downwards like a waterfall:

```
Requirements → Analysis → Design → Implementation → Testing → Maintenance
```

**Advantages:**
- Clear documentation at each stage
- Easy to manage — each stage has defined deliverables
- Works well when requirements are **fixed and well understood**

**Disadvantages:**
- Inflexible — very expensive to go back and change earlier stages
- Customer does not see working software until late in the project
- Poor fit when requirements may change

### Agile methods

An **iterative, incremental** approach. Software is built and improved in cycles called **iterations** (or sprints). Stakeholders review progress regularly.

**Key principles (from the Agile Manifesto):**
- Working software over comprehensive documentation
- Customer collaboration over contract negotiation
- Responding to change over following a plan
- Individuals and interactions over processes and tools

**Advantages:**
- Flexible — requirements can change between iterations
- Working software produced early
- Regular stakeholder feedback reduces risk of building the wrong thing

**Disadvantages:**
- Less documentation — harder to maintain later
- Scope creep — new features keep being added
- Requires close collaboration; hard for large, distributed teams

### Extreme Programming (XP)

An agile method with additional practices:
- **Pair programming** — reduces bugs through continuous peer review
- **Test-driven development** — write tests first, then code to pass them
- **Small releases** — deliver working software frequently
- **Continuous integration** — code merged and tested multiple times a day
- **Refactoring** — code quality is continuously improved

### Spiral model

Combines **iterative development** with **risk analysis**. Each loop of the spiral has four phases:

```
Plan → Risk Analysis → Develop & Test → Evaluate
```

- Each loop produces a prototype or increment
- **Risk analysis** distinguishes it from other models — risks are identified and addressed each cycle
- Suited to **large, high-risk projects**
- Can be expensive due to the overhead of repeated risk analysis

### Rapid Application Development (RAD)

Focuses on speed by:
- Building **prototypes** quickly
- Involving users heavily to refine the prototype
- Iterating until the prototype becomes the final product

**Advantages:** Fast delivery; user-driven; good for UI-heavy applications  
**Disadvantages:** May sacrifice performance or security for speed; relies on active user involvement

### Choosing a methodology

| Scenario | Suitable methodology | Reason |
|----------|---------------------|--------|
| Requirements are fully known; safety-critical system | Waterfall | Rigid process suits fixed requirements |
| Requirements likely to change; customer involvement high | Agile (Scrum/XP) | Flexible; stakeholder feedback built in |
| Large, complex project with significant technical risk | Spiral | Risk analysis each cycle reduces chance of failure |
| Tight deadline; UI prototype needed quickly | RAD | Prototyping speeds up development |

### Testing types

| Type | Description |
|------|------------|
| **Unit testing** | Testing individual modules/functions in isolation |
| **Integration testing** | Testing how modules work together |
| **System testing** | Testing the complete system against requirements |
| **Alpha testing** | Internal testing before release |
| **Beta testing** | Limited release to real users for feedback |
| **Acceptance testing** | Client verifies the system meets agreed requirements |

**Test data types:**
- **Normal data** — valid inputs within expected range
- **Boundary data** — values at the exact edges of the valid range
- **Erroneous data** — invalid inputs that should be rejected

## Worked examples

### Example 1 — Selecting a methodology

**Scenario:** A small start-up is building a new social media app. They have a rough idea of the features they want but expect requirements to change based on user feedback.

**Best methodology:** Agile (e.g. Scrum)  
**Reason:** Requirements are not fixed, customer collaboration is possible, and small frequent releases allow the team to adapt based on real user feedback.

---

### Example 2 — Test-driven development trace

A developer is implementing a function `double(n)` using TDD:

1. Write a failing test: `assert double(5) == 10`
2. Write the minimum code to pass: `FUNCTION double(n) RETURN n * 2 ENDFUNCTION`
3. Run the test — it passes
4. Refactor if needed; repeat for next test case

## Common mistakes

- ❌ **Mistake:** Saying Agile has no documentation at all.  
  ✅ **Correction:** Agile prioritises *working software* over *excessive* documentation — some documentation still exists.

- ❌ **Mistake:** Saying the Waterfall model can easily go back to earlier stages.  
  ✅ **Correction:** Waterfall is sequential — going back is expensive and disruptive; this is a key weakness.

- ❌ **Mistake:** Saying pair programming halves productivity because two people write one piece of code.  
  ✅ **Correction:** Pair programming typically *increases* quality and reduces bugs, often resulting in better net productivity.

- ❌ **Mistake:** Confusing alpha and beta testing.  
  ✅ **Correction:** Alpha = internal; Beta = limited external/real users.

## Quick-check questions

1. List the stages of the Waterfall model in order.
2. What is a sprint in agile development?
3. Give one advantage and one disadvantage of the Agile approach compared to Waterfall.
4. What makes the Spiral model different from other iterative models?
5. What is test-driven development?
6. What is the difference between alpha and beta testing?
7. Give an example of boundary test data for a field that accepts ages 0–120.

<details>
<summary>Outline answers</summary>

1. Requirements → Analysis → Design → Implementation → Testing → Maintenance
2. A fixed time period (e.g. 1–4 weeks) in which the team develops an agreed set of features.
3. Advantage: flexible to changing requirements / working software produced early. Disadvantage: less documentation / scope creep possible.
4. Includes formal **risk analysis** at each iteration/cycle.
5. Writing automated tests before writing the code, so code is written specifically to pass the tests.
6. Alpha: internal testing by developers/staff. Beta: testing by a limited group of real end-users.
7. 0, 1, 120, 119 (boundary values); e.g. -1 and 121 are erroneous.

</details>
